# M9 — useful Linux userspace (BusyBox on Clean-Slate)

M9 runs an unmodified, statically linked BusyBox under the Linux x86-64
compatibility personality, on Clean-Slate's own process, capability, storage
(M5/M6) and network (M7) services. Linux is a personality, not the native ABI.
The per-lane contracts live in [LINUX_PERSONALITY.md](LINUX_PERSONALITY.md),
[M9_ABI_INVENTORY.md](M9_ABI_INVENTORY.md), [M9_ADDRESS_SPACE.md](M9_ADDRESS_SPACE.md)
and [M9_BLOCK_WAKE.md](M9_BLOCK_WAKE.md). This page covers the milestone as a whole
and its acceptance gate.

## Authoritative gate: `cargo xtask test-m9`

Aliases: `m9`, `m9.9`. The host prints `[M9  ] PASS` only after every step below
succeeds. Each step prints `[M9  ] step N/17 <name>` first, so a failure names its
step. Every build, host test and QEMU boot runs under a finite timeout (builds
20 min, host tests 15 min, each QEMU boot has its own per-test bound). None of it
uses the Internet or host services: the M7 peer is an in-process hermetic fixture.

`scripts/run-tests.ps1` / `run-tests.sh` register `test-m9` as an Aggregate. Every
`test-m9-*` constituent and `verify-m9-fixture` is marked as covered by `test-m9`,
so `-Exhaustive` / `--exhaustive` runs each of them exactly once, inside `test-m9`.
Name a constituent explicitly to debug it alone. CI (`.github/workflows/pr.yml`)
runs `test-m9` through the exhaustive acceptance job; the check job no longer
repeats the fixture verification or the rootfs host tests.

## The convergence boot (`test-m9-userspace`)

Kernel feature `m9-userspace-self-test`; module `kernel/src/selftest/m9_userspace.rs`.
Everything goes through the production path: the rootfs image is parsed and
integrity-checked, the namespace is built, and every command is started with
`launch_linux_process_with_authority` as `/bin/sh -c '<command>'` at the
conventional low address, with envp `PATH=/bin`. BusyBox itself runs `fork`,
`execve`, `wait4`, `pipe`, `dup2` and so on through the real syscall handlers.

Per cycle (9 cycles):

1. **Exact matrix.** All 18 entries of `fixtures/busybox/frozen/commands.toml` run in
   file order. Each must exit with its exact status. In cycle 1 the full stdout is
   dumped as `[M9  ] stdout cmd= off= hex=` and checked against the entry's
   `stdout` / `stdout_prefix` / `stdout_contains`. Later cycles must reproduce
   cycle 1's length and FNV-1a hash byte for byte.
2. **Denials.** Five probes, each must exit 1 with empty stdout:

   | Probe | Command | Launch authority | Required evidence |
   |-------|---------|------------------|-------------------|
   | `deny-fs-readonly` | `echo x > /etc/hostname` | full | `Read-only file system`, no capability denial (EROFS comes from the namespace) |
   | `deny-tmp-write` | `echo x > /tmp/denied` | no tmp objects | `[CAP ] deny holder=<pid> … op=write reason=no-authority`, `Permission denied` |
   | `deny-tmp-read` | `cat /tmp/script.sh` | no tmp objects | `[CAP ] deny … op=read reason=no-authority`, `Permission denied` |
   | `deny-net` | `wget -O - http://m7.fixture.test:4001/` | no network | `[NET ] denied pid=<pid> reason=no-authority` |
   | `connect-timeout` | `wget -O - http://203.0.113.1:9/` | full | `Operation timed out` after a genuine block |

3. **Resources.** `[M9  ] resources label=cycleN` must equal the pre-launch
   baseline for every reusable pool: Linux proc rows, threads, processes, fd tables,
   open descriptions, pipes, Linux waiters, sockets, net and object request slots,
   capabilities, Linux mm and signal rows. `/tmp` files and namespace nodes are what
   the matrix legitimately leaves behind, so they must stay equal to cycle 1.

The BusyBox bytes in the rootfs are checked against the build-time pins (CRC-32 and
length, generated by `kernel/build.rs` from the verified binary) before the first
launch (`[M9  ] busybox verified`) and after the last cycle (`[M9  ] busybox intact`).
Nothing patches the fixture at runtime.

### Blocking proof

A native userspace sibling (scheduler slot 5) loops on the native `VERSION`
syscall, and each such call counts one unit of native progress. Scheduler hooks in
`sched/wait.rs` record the progress count and the tick when a Linux thread blocks,
and compare them when it is woken or times out. `[M9  ] blocking PASS` requires at
least one Linux wake with native progress in between and a non-zero blocked
interval. `[M9  ] timeout PASS` requires the unreachable connect to block for at
least 2 ticks with native progress, then fail with `ETIMEDOUT`. The M7 TCP connect
timeout fires before the Linux-side deadline, so this is a genuine wake carrying
the error, not a poll loop. Every sleep line also reports blocks, wakes and
timeouts per command.

### Host validation

After the ordered markers, `xtask/src/m9_userspace_validate.rs` re-parses the whole
serial log. It checks: matrix order and exact status for every cycle; cycle-1
stdout rebuilt from the hex lines and checked against `commands.toml`; identical
output hashes in later cycles; probe order, status and denial lines attributed to
the probe's pid; the launch sequence; the blocking counters; resource equality
with the baseline; and pinned hashes in the integrity lines. It prints
`[M9  ] host validation ok`. Any guest `[FAIL]` ends the run immediately.

## Namespace

| Path | Backing | Access |
|------|---------|--------|
| `/`, `/bin`, `/etc` | embedded `CSROOTFS` image | read-only; writes and `mkdir` return `EROFS` |
| `/bin/<applet>` | image link → `/bin/busybox` | exec keeps the original path so BusyBox selects the applet |
| `/etc/hostname` | image file | `m9-fixture\n` |
| `/etc/resolv.conf` | image file | `nameserver 10.77.0.1` (hermetic M7 DNS) |
| `/tmp` | M6 persistent objects `0x4C0000`..`+4` via the M5/M6 object service | read needs READ, create/write/`mkdir` need WRITE on the tmp objects; otherwise `EACCES` plus a `[CAP ] deny` audit line |

Linux launches get tmp object and network capabilities only when their
`LinuxLaunchAuthority` says so. `fork` delegates the parent's capabilities.
File descriptors are compatibility-local integers and never carry authority.
Limits: 64 namespace nodes, 8 `/tmp` entries, 512 bytes per `/tmp` file,
`LINUX_PATH_MAX = 256`.

## Syscall families

| Family | Syscalls | Accepted flags / notes |
|--------|----------|------------------------|
| fd core (#147) | `read`, `write`, `writev`, `close`, `dup2`, `fcntl`, `lseek` | `fcntl` `F_GETFD`/`F_SETFD`/`F_GETFL`/`F_SETFL`/`F_DUPFD_CLOEXEC` |
| fs (#101) | `open`, `stat`, `lstat`, `getcwd`, `mkdir`, `getdents64` | `open` `O_RDONLY`/`O_WRONLY`/`O_RDWR`, `O_CREAT` (writable access only), `O_TRUNC`, `O_DIRECTORY`; other bits such as `O_LARGEFILE` and `O_CLOEXEC` are not rejected |
| process (#102/#146) | `fork`, `execve`, `wait4`, `pipe`, `getppid`, `exit`, `exit_group` | `wait4` blocking or `WNOHANG` (other option bits outside the Linux set are `EINVAL`); pipe write without readers is `EPIPE` (no `SIGPIPE`) |
| runtime (#103) | `arch_prctl`, `brk`, `mmap`, `munmap`, `clock_gettime`, `nanosleep`, `poll`, `ioctl`, `getpid`, `geteuid`, `rt_sigaction`, `rt_sigprocmask`, `set_tid_address`, `uname` | anonymous `MAP_PRIVATE`/`MAP_ANONYMOUS` only, `PROT_EXEC` together with `PROT_WRITE` rejected; `poll` `POLLIN`/`POLLOUT`/`POLLERR`/`POLLHUP`/`POLLNVAL`; `ioctl` `TIOCGWINSZ` returns `ENOTTY` |
| socket (#105) | `socket`, `bind`, `connect`, `sendto`, `recvmsg` | `AF_INET` with `SOCK_DGRAM`/`SOCK_STREAM`, `SOCK_CLOEXEC`, `SOCK_NONBLOCK`; brokered onto M7 `NetworkRequest`s |

Every blocking call (pipe read/write, `wait4`, `nanosleep`, `poll`, `/tmp` object
I/O, socket I/O and connect) parks the thread with `block_linux_syscall` on a
namespaced wait key and restarts idempotently after wake or timeout. The wait-key
table is in [M9_BLOCK_WAKE.md](M9_BLOCK_WAKE.md).

## Unsupported behaviour

- Any syscall not listed above returns `-ENOSYS` and the process continues. The
  diagnostic `[LNX ] unsupported syscall=<nr>` is budgeted per process. BusyBox
  `mkdir -p` calls `umask` (95), gets `ENOSYS`, and carries on.
- No signal delivery. Dispositions and masks are recorded only, so `kill`, job
  control and `SIGPIPE` are absent.
- No `/dev`, `/proc` or `/sys`. No terminals: stdio is the console projection and
  `TIOCGWINSZ` returns `ENOTTY`.
- No dynamic linking, PIE, `PT_INTERP` or threads (`clone` with `CLONE_VM`).
- No listening sockets (`listen`/`accept`), no IPv6, no `sendfile`.
- Everything outside `/tmp` is immutable.
- The environment is exactly what the launcher passes (`PATH=/bin` for the
  acceptance shell).

## Tracing workflow

Build with feature `m9-linux-trace` to record every Linux syscall into a bounded
ring. It emits `[LTRC] pid=<pid> gen=<gen> <name>(<scalar args>) -> <value|errnoN> <reason>`,
where the reason is one of `ok`, `unsupported`, `bad-pointer`, `denied-authority`,
`not-found`, `would-block`, `blocked`, `woke`, `timeout` or `other-errno`. Output is
rate-limited to 64 global and 32 per-process tokens, refilled at 2 per tick.
Anything dropped is reported as `[LTRC] dropped=<n> pid=<pid>`. `cargo xtask
test-m9-linux-trace` proves the tracer itself.

To investigate a failing matrix command:

1. Run `cargo xtask test-m9-userspace`. The failing `[M9  ] cmd=` line or the host
   validator names the command, cycle and mismatch (status, stdout bytes, or
   evidence), and the `[M9  ] stdout … hex=` lines hold the exact bytes.
2. Compare against the reference trace `fixtures/busybox/frozen/traces/<name>.strace`
   for the syscall sequence BusyBox expects on Linux.
3. For a guest-side trace, temporarily add `"m9-linux-trace"` to the feature list
   in `run_m9_userspace_acceptance` (`xtask/src/main.rs`) and rerun. Match
   `[LTRC]` lines by pid against the `[M9  ] shell started pid=` line for that
   command. Remove the feature again before committing.
